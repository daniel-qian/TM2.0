# ADR-0033 · locale 进契约，后端不再产出人话

- 日期：2026-08-03
- 状态：已定（Danny grill ×3 轮逐项拍板，PRD `.issues/locale-contract-0803/prd.md`）
- 前情：[ADR-0020](0020-avery-graduates-from-demo-only-to-live-lite-product.md)（live 产品化，
  `/advise` 契约成形时没有语言这个概念）→ [ADR-0018](0018-renqingwei-demoted-to-redline-product-truth-decision-layer.md)
  （红线：可溯源、不替客户断言——本 ADR 的「引文不翻译」直接由它推出）。

## 背景：语言从来不是被设计的，是长出来的

产品最初的判断是**不在境内找用户**，所以英文是代码默认（`VITE_AVERY_LOCALE || 'en'`），
中文是后来一路补进去的。2026-08 要和三亚一家公司对接，中文第一次成为**真实客户需求**，
这个历史欠账才被迫结账。

盘点下来，语言在这个产品里其实有**三个互相独立的面**，它们今天可以各说各话：

| 面 | 现状 | 谁决定 |
|---|---|---|
| ① 界面壳文案 | 已双语（`src/shared/i18n/`） | 前端 `?lang= > VITE_AVERY_LOCALE > en` |
| ② 后端模板文案 | **写死中文**（`decision_rules.py` / `decision_grading.py` 等） | 没人——常量 |
| ③ LLM 判读正文 | **不受控**（prompt 里没有任何语言指令） | 涌现，大概率跟着文档语言 |

于是"英文用户拿到中英夹杂的核心判读面板"只是症状；根因是 **`AdviseRequest` 契约里
压根没有 locale 字段**——判读用什么语言，从来不由用户控制。

还有第四个东西必须和上面三个分开，否则一定会被误伤：

**④ 输入侧检测词表/正则**（`extract.py` 93 条、`redline.py` 75 条、`granularity.py` 40 条…）。
这些中文是用来**读中文文档**和守红线的匹配模式。它们必须永远是中文，**与界面语言无关**。
把它们"一并双语化"＝把解析能力和红线砸了。

## 决定

1. **locale 是请求字段**。`AdviseRequest` 加 optional `locale`，前端把它已有的解析结果
   （`?lang= > VITE_AVERY_LOCALE > en`）随请求传下去。**缺省 `en`、非法值回落 `en` 并告警**
   ——与前端解析链末端同一个默认值，一条链只许有一个兵家必争之地。

2. **后端不再产出人话**。规则推导出来的那些句子（`按规则判为X：Y。`／`未读到：…`／
   `…写的是「X」，无法确定具体日期`）本来就是结构化事实的字符串拼接，改为
   **只回机器键 + 结构化字段**，句子由前端用 i18n 表渲染。

3. **LLM 正文语言进 prompt**。把 locale 显式写进 scaffold，要求用该语言作答；
   并立门断言"正文语言 == 请求 locale"，否则这条会无声退化。

4. **引文（evidence）永不翻译**。三亚客户的文档是中文的，英文界面下引文仍是中文原样。
   `evidence` 是逐字引用，翻译就等于"编"，直接违反[ADR-0018](0018-renqingwei-demoted-to-redline-product-truth-decision-layer.md)
   的可溯源红线。周围的标签/说明走英文，引文本身不动。

5. **输入侧词表/正则一个字不动**。「文档语言」≠「界面语言」。英文文档解析是另一个量级的
   活（词表、正则、红线词族全要英文版 + 各自的验收语料），**单开一票**，不在本票。

6. **真双语对等**：zh / en 都是一等公民，不做"锁 zh、en 只求不跑偏"的降级方案。

## 🔴 本 ADR 反转了一条既有决策

`src/lite2/homeDerive.ts` 与 `HomeScreen.tsx` 里白纸黑字写着：
**「前端不硬编码「高风险/需确认/可推进」这三个词，label 一律取自 payload 的 `grade_label`」**。
决定 2 要求前端自己出词，与这条直接冲突。

**保留它的用意，更换它的载体。** 那条规矩真正要防的是「同一个档位，前后端各说各的词」——
它要的是**单一事实源**，不是"必须由后端发"。改法：后端发机器键 `grade`（`high_risk` 等），
前端查**唯一**那张 i18n 表。事实源仍然只有一份，前端仍然不"自拟"——它是查表，不是发挥。

反过来说，旧写法在双语下反而**做不到**单一事实源：后端要为两种语言各存一份词，
前端 i18n 表里还得再存一份给别处用，那才是真的会漂。

## 后果

- 契约**一刀切换**，不做新旧字段并存：这是 demo 原型、零外部 API 消费者、前后端同仓同步发。
  并存反而会留下"后端仍在产出中文"的破口，而那正是本票要铲掉的东西。
  同批要改的消费方：前端 `homeDerive.ts` / `HomeScreen.tsx` / `transport.ts`、
  4 道门（cr-alignment / home-skeleton / topbar-clearance / capture-align-board）、
  `tests/test_decision_grading.py`。
- 需要一道**双语门**（本票新增），否则文案类缺陷必然回归。
- `ask_api.py` 那 40 条问卷文案（发给员工的 H5）**不在本票**——那是另一条用户旅程
  （收件人是员工不是经理），语言来源可能都不同。单开一票。
