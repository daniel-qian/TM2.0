# ADR-0029 · 满态对齐走真管道，不走 demo 注入

日期：2026-07-22 · 状态：Accepted · 拍板：Danny（满态对齐盘问 · 决策批①）

## 背景

「布局与真部件」三批战役完成了**皮对齐**（design token/骨架/密度，规格门 35/35 全绿），
但 Danny 并排实测后判定离目标仍远——因为他要的是**满态对齐**：并排开两个 app，观感一样
丰富。她的丰富度来自 进度%/里程碑/风险徽章/成员负载/方法库 等字段——我方**数据模型、
抽取器、语料**三层都没有。

诱惑是抄近路：给示例团队直接灌一份结构化满数据（跳过抽取管道），最快见效。

## 决策

**富字段一律走真管道；demo 的丰富度来自富语料，不来自注入。**

1. 数据模型 + 抽取器扩展出「进度/里程碑/风险/人员负载/情绪」等槽位——文档里写了就抽，
   没写就该行收起（absent≠none 不变）。
2. demo 满态靠**三亚富语料**：原创虚构度假酒店语料（基于
   `D:\Boyle\research\sanya-lushan-yiju-hotel\` 的脱敏调研与 0721 脱敏 seed 扩展；
   人名用小王/小张式一眼好记的代号；成稿免审——Danny 2026-07-22 拍板），把富字段
   **写进文档**，经真抽取长出满态。
3. **禁止** UI 写死演示内容、禁止 demo-only 数据注入路径——feat-068 已为「URL 挂参数
   看到编造内容」把 stub 通道从生产 DCE 掉，这是同一条纪律的延伸。
4. 方法库（playbooks）内容同理：语料里写 SOP 文档 → 抽取成方法卡；非 demo 空态维持
   coming-soon 诚实标。

## 备选与否决理由

- **demo 直灌**：最快，但部件只有 demo 有数据——真客户上传后满屏「文档未提及」，
  产品裂成演示版/真实版两张脸。否决。
- **先注入后补管道**：演示不等人时的折中，但中间态要维护两条数据路。否决——
  语料写全后真管道同样能撑起演示，且资产可复用（feat-019 换皮首例）。

## 影响

- 语料成为一等资产：换一个行业客户 = 换一套语料，UI/管道零改动（ADR-0021 包/皮思路）。
- 真客户文档薄 → 字段收起，界面自动降级为诚实稀疏态，无需分支。
- 抽取器语法即语料语法：字段怎么写才抽得出，随字段落地一并文档化（语料作者可依）。
