## 1. 病：单字否定前瞻挡不住否定短语

`_norm_status` 的四条中文梯子各自带一个**单字**否定前瞻：

```python
_ZH_AT_RISK  = r"(?<![无没])风险|延期|..."
_ZH_DONE     = r"(?<![未没待])完成|已交付|..."
_ZH_ON_TRACK = r"进行中|推进中|(?<![不异])正常|按计划|如期|顺利|在轨"
_ZH_BLOCKED  = r"受阻|已阻断|阻塞|卡住|..."      # 一个前瞻都没有
```

单字前瞻只能往回看**一个**字，而中文用**短语**否定：「无法」的「法」、「未能」的「能」、
「没有」的「有」、「未发现」的「现」都不在那几个字表里，于是整句穿过前瞻直接命中关键词。

### 实测（跑出来的，不是读正则推的）

| 文档原话 | 修复前读作 | 性质 |
|---|---|---|
| 无法完成 / 未能完成 / 不能完成 / 没能完成 / 难以完成 / 无从完成 | `done` | 🔴 **反向** |
| 无法按时完成 / 未能如期完成 / 无法如期完成 / 本季度难以完成收尾 | `done` | 🔴 反向 |
| 未能如期交付 | `on-track` | 🔴 反向（命中「如期」）|
| 没有风险 / 未发现风险 / 无明显风险 / 无重大风险 / 不存在风险 / 未出现风险 | `at-risk` | 假警报 |
| 没有延期 / 不会延期 / 未见滞后 / 不存在逾期 / 没有落后 | `at-risk` | 假警报 |
| 未按计划推进 / 没有按计划推进 / 不按计划 / 未能如期 / 无法如期 | `on-track` | 🔴 反向 |
| 进展不顺利 / 不太顺利 / 不够顺利 / 不是正常 / 不太正常 / 不在轨 | `on-track` | 🔴 反向 |
| 未受阻 / 没有受阻 / 不存在阻塞 / 没有卡住 / 不会停工 / 未搁置 / 不再搁置 / 没有停滞 | `blocked` | 假警报 |

共 **48 条**。任务书点名要查的三条（「并非没有风险」「不是正常」、`_ZH_BLOCKED` 有没有同型不足）
全部查了，结论在 §4。

### 为什么是 blocker：下游把它反向放大

`status="done"` 正是 `decision_grading._m_done` 读的字段。整条链在**旧代码上**跑出来的原话：

## 2. 修：一个共用的、边界精确的否定扫描

四条梯子不再各自带前瞻，改共用 `_zh_negation_depth` / `_zh_states`
（`eval-harness/avery/ingest/extract.py`）。

**刻意不是滑动窗口。** `redline._negated` 用 32 字窗口，那正是 B3（「别墅」把红线整段关掉）的
成因：附近任何地方出现一个否定字，后面全部失效。这里否定必须**正好结束在关键词开始的位置**
才算数，所以下面这些**按构造**通过，不需要白名单：

| 词 | 读作 | 为什么不被误伤 |
|---|---|---|
| 未来风险较大 | `at-risk` | 「未」和「风险」中间隔着「来」，「来」不是连接字 |
| 非常正常 | `on-track` | 「非常」是 very |
| 不过完成了 | `done` | 「不过」是 but |
| 无论如何都要如期交付 | `on-track` | 「无论」是 regardless |

（B3 的结论原话是「别墅白名单几乎什么都修不了」。这里不用白名单是同一条道理。）

### 两处刻意的不对称

**其一：`_ZH_CANNOT_DELIVER` → at-risk，不是留白。**
「未完成」是中性事实（还没做完 = 正在做），保持留白；「无法完成」是项目在告诉经理它会 miss。
把后者压成留白是诚实但装聋，而且那个留白到了 decision_grading 就变成「文档没陈述状态」——
对一份写得清清楚楚的文档说这句话，本身又是一次失实。所以「无法/未能/不能/没能/难以/无从」+
（按时/按期/如期/准时/及时）+（完成/交付/上线/结项/验收/完工/竣工/收尾/达成）→ at-risk。
这是**读出来的，不是编出来的**。

**其二：双重否定，正负两侧不同待遇。**
`_zh_negation_depth` 数层数而不是给 True/False，因为中文双重否定的两个方向意思相反：

- 「并非没有风险」= 确实有风险 → `at-risk`（depth 2 当 depth 0 用）
- 「不无风险」= 有风险 → `at-risk`（修复前读成留白，「无」把它挡掉了）
- 「并非无法完成」= 还有机会做完 **≠**「已完成」→ 留白（正面档 `positive_claim=True` 要求 depth 严格为 0）

正面档（done / on-track）要求 depth 严格为 0，风险档只要求偶数。理由和 `risk_only` 那段一样：
可推进必须建立在**明确的正面自报**上，一句反驳不是自报完成。

保留的两个前瞻 `(?<![待])完成` / `(?<![异])正常` **不是否定**（「待」是 pending，「异」是
abnormal），刻意留在各自模式里，没有混进共用机制。

## 7.1 🔴 第一轮自己造出来的 blocker：「不得不」被数成单重否定

这条最重要，因为它和第一轮要修的那条**方向完全一样**，而且是修复引入的。

```
不得不推迟        3ef4224: 'at-risk'  →  第一轮: ''
不得不延期上线    3ef4224: 'at-risk'  →  第一轮: ''
不得不停工整改    3ef4224: 'blocked'  →  第一轮: ''
不得不搁置 / 不得不中止  同上
因集团批复未下，本月不得不推迟上线   'at-risk' → ''
```

**成因**：「不」紧贴关键词 → `_ZH_NEG_RE` 命中 → depth=1；再往回扫「不得」时「得」不在
`_ZH_NEG_LINK` 里，外层那个「不」数不进来。于是**中文最常见的双重否定成语被数成单重否定，
直接反号**。对照组「不是没有风险」两轮都对——只因为「是」碰巧在表里。

**这同时证伪了第一轮报告 §5 note 4 自己写下的安全性论证**：
「没覆盖的连接字会退回『不识别为否定』，即回到修复前的行为，不会产生新的错误方向」。
错。在**双重**否定里，漏一个连接字不是少认一层，是把 depth 从 2 打成 1，奇偶翻转 → 反号。
这条论证已在 `extract.py` 的注释里就地改写。

**修法**：`得` 进 `_ZH_NEG_LINK`。两个方向都钉：

| 文档原话 | 语义 | 读数 |
|---|---|---|
| 不得不延期 | 被迫延期 = 陈述了风险 | depth 2 → `at-risk` |
| 不得延期 | 规定不许延期 = 不是状态自述 | depth 1 → `""` |

门：`test_the_bu_de_bu_idiom_is_two_negations_not_one`（10 条）+
`test_bu_de_and_bu_de_bu_are_different_readings`（把「得」的**两个方向**同时钉住——
加一个链接字总能让 BORN RED 变绿，难的是证明它没吃掉相邻读数）。

## 7.2 `_ZH_DONE` 射程：白名单外的缺口按同一条链输出同一句失实的话

复核加的对抗语料，第一轮代码上**原 bug 原样活着**。全部已修（`'done'` → `'at-risk'`）：

```
没办法完成 / 没办法按时完成 / 没法完成 / 无办法完成
很难完成 / 太难完成 / 极难完成
不太可能完成 / 基本不可能完成 / 不可能完成
无把握完成 / 没把握完成 / 没信心完成 / 无信心按时交付
不确定能否完成 / 不会按时完成 / 不会如期完成 / 无力完成
完成不了 / 验收通过不了 / 交付不了 / 这个月怕是完成不了
来不及完成 / 赶不上完成
```

三类新构造，每一类都保持**边界精确**：

1. **度量副词 + 难**：`很难/太难/极难…`。**刻意不接受裸「难」**——否则「克服困难完成了交付」
   会被读成否定。困 / 灾 / 万 不是度量副词，所以 困难 / 灾难 / 万难 按构造够不着。
2. **V不C 可能补语**（`赶不上` / `来不及`）：`[一-鿿]不(?:了|上|及|起|动|完|下)`。
   多 / 定 不在补语表里，所以 差不多 / 说不定 按构造够不着。
3. **后置否定** `_ZH_POST_NEG_RE`：中文把可能补语放在动词**后面**，反向扫描按构造看不见。
   「完成不了」第一轮读成 done。修法是在 `_zh_states` 里给后置否定 +1 depth。
   🔴 **「不成」刻意排除**：「按时完成不成问题」「如期交付不成问题」是好消息，
   当成否定就是反号——和 7.1 一模一样的错误，不重犯一次。

`不确定能否` 要求 `能否/可否/是否` **必须出现**：否则「尚不确定风险是否可控」会被压成 `""`，
丢掉文档陈述的风险。已在控制组里钉。

## 7.3 `_ZH_ON_TRACK` 同型不足 + 「压成留白」在产品表面不成立

**第一层（仍然反向，已修）**：第一轮链接字表收了「太」「够」，没收「算」「甚」「很」「大」：

```
不算顺利 / 不甚顺利 / 不大顺利   'on-track' → 'at-risk'
不很正常                         'on-track' → ''
```

**第二层（复核说得对，我改了设计）**：第一轮把「未按计划推进 / 进展不顺利」从**反向**救到了
**留白**，但复核从真 payload 验出来，留白到经理眼前**又变回 on-track**：

```
registry.py  project_cards()   `if pr.status:`        → status="" 时整个键不写进 wire
teamData.ts  :159              `card.status ?? 'on-track'`  → `??` 只吃 null/undefined，
                                                             键缺失正好命中 → 编出 on-track
```

**经理看到的东西和修复前一模一样**，只是决策卡理由从「项目自报正常」换成了「没读到状态…
任何一项」——而文档第三行就写着「进展不顺利」。两句都是产品在说客户文件里没有的话。

所以第二轮**改了设计**：客户写下的负面陈述不再压成留白，照读落 `at-risk`（新增 `_ZH_OFF_PLAN`）。

| | 读数 | 理由 |
|---|---|---|
| 未按计划推进 / 没有按计划推进 / 未按原计划执行 | `at-risk` | 文档**陈述**了偏离，不是缺失 |
| 进展不顺利 / 不太顺利 / 不够顺利 / 进展不理想 / 进展不乐观 | `at-risk` | 同上 |
| 不是正常 / 不在轨 / 不很正常 / 不按计划 / 未能如期 | `""` | 否定掉的是**标签本身**，归不出方向，留白才诚实 |

「留白 = 诚实」这条论证第一轮写得太满，已在 `_ZH_OFF_PLAN` 注释里就地纠偏：留白只对
**真的读不出方向**的成立；对**读得出方向的负面陈述**，留白等于替客户否认他写过的话。

同一条否定扫描仍然管着它，所以「并非不顺利」「没有不顺利的地方」**不**开火（已钉门）。

## 7.4 误报侧：复核说「量了，但没量到自己最会出事的地方」——重量一遍
