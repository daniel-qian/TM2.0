## 0 · 这一波要解决什么

## 3 · 功能规格

### G1 账号体系（Supabase auth）· P0

**目的**：三家公司各自有账号，之后还会发给更多公司。
**做**：Supabase auth（邮箱 + 密码起步）；注册 / 登录 / 登出 / 会话恢复。
**映射口径（关键，别拆错）**：`Supabase user → 公司 context_id`。**`owner_token` 保留在下层不动**——服务端按 user 查到 context 再取 token，前端不再手工持有/传递 token。这样 feat-038 的租户隔离原样复用，不返工。
**不做**：多角色权限、组织邀请、SSO/OAuth。一家公司一个账号起步（Danny：不要过度设计、不造轮子）。
**要处理**：现有匿名 context 的归属——给一条"认领"路径，或登录后直接新建，二选一即可。
**验收**：两个账号各自登录，只能看到自己公司的人/项目；换账号后旧数据不串。

### G2 路由化（router + 深链）· P0

**目的**：能发链接、后退键正常、刷新回到原处。
**做**：引入 react-router，把现在的 Zustand `screen` 变量换成真路由。
- 7 屏：`/team` `/room` `/followups` `/notes` `/closer-look` `/playbooks` `/vision`
- 深链：`/team/:personId`（人卡）、`/projects/:projectId`（项目详情）
- **接力**：`/room?q=<问题>` —— 对应她的「深入问 Nexus」，从决策卡带着问题进议事室
- 软删除显示开关：`?showInactive=1`
**必须不破坏**：现有 `?v=2&mode=live&skin=paper&lang=zh` 这几个既有 query 参数。
**别抄的坑**：她的 `?highlight=id` 是**死链**（`/people` `/projects` 根本不读这个参数），不要照抄这个形状。
**验收**：复制任意深链到新标签页能直达；浏览器后退在屏间正常回退，不掉出应用。

### G3 会话不丢（contextId 恢复）· P0 · 最便宜的一条

**目的**：修掉"刷新就丢全部团队数据"——这是 handoff 里挂着的已知问题，也是我这次没能把 seed 灌进 UI 的直接原因。
**病因**：`src/lite2/store.ts` 的 `contextId` 初始化为 `null`，加载时**不从 localStorage 恢复**；而后端早已持久化（Supabase）。`ownerToken` 其实已经存了（`lite2:ownerTokens:v1`），只差 contextId。
**做**：存住 `contextId`，加载时按它走 `/team/{id}` 重新拉。handoff 原话「纯前端几行」。
**与 G1 的关系**：不冲突。G3 先落（几行、立刻见效），G1 落地后 `contextId` 的来源从 localStorage 改为服务端按账号返回，G3 的恢复逻辑退化成兜底。
**验收**：上传 → 刷新 → 团队数据还在；关掉浏览器重开还在。

### G4 聚合首屏 +「今天要决策的」· P0

**目的**：Danny 拍板"聚合首屏和分屏**结合**，两个都极端"。
**做**：新增一个聚合入口屏，**7 个分屏全部保留**为深入面。聚合屏含四块摘要，每块可点进对应分屏：
1. **今天要决策的**（按 G5 定级排序，带待处理计数）← Danny 明确点名
2. 差距摘要（→ 多看一眼）
3. 需关注的人（→ 你的团队）
4. 团队概览计数
**不做（本波）**：她的 5 张 KPI 指标条——我们没有那些量（见 G11）。**尤其不要照抄她硬编码的问候统计句**（"扫描了 186 条信号""距国庆还有 83 天"全是写死的假数据）。我们的 signals 是真的，要算就真算。
**「需关注的人」筛选口径**：她用 `load>=90 或 sentiment=strained`——**这两个字段我们都没有**。本波先用可得信号（关联 blockers、在 signals 中被提及次数）；G10/G11 落地后再换成真口径。
**验收**：聚合屏每块的数字都能追到真数据来源，没有一个是写死的。

### G5 决策定级（规则定级 + Avery 写理由）· P0

**目的**：「今天要决策的」需要排序和分级；她那三档标是**人手敲进假数据的**，我们的决策是自动长出来的，必须有口径。
**做（Danny 拍板 a+b）**：
- **规则算等级**（确定、可复现）：三档 `高风险 / 需确认 / 可推进`
- **Avery 写那句人话理由**（等级归规则，文字归它）
- **允许 Avery 上调**（补规则盲区），**必须写明为什么**
- 🔴 **禁止 Avery 下调**——漏报比误报贵，尤其对方拿真文件来试
**规则可用依据（基于实测真 payload 覆盖率，不是想象）**：

| 信号 | 覆盖 |
|---|---|
| `signals` 关键词（流失/投诉/冲突/离职） | 17/17 |
| `blockers` | 13/17 |
| `status`（at-risk / blocked） | 13/17 |
| `dueDate` 迫近 | 7/17 |
| `progress` 落后 | 6/17 |

后两项覆盖只有三分之一 → **纯规则必有盲区，这正是留给 Avery 上调的口子**。
**硬要求**：定级口径落成**一份可读的配置/文档**，不许埋进 prompt。三家公司一定会问"凭什么说这条高风险"，要能当场把表给他看。
**验收**：同一份文件连跑两次，等级完全一致；每条决策都能展开看到命中了哪条规则。



### G6 应用内草稿框 · P0 · Danny 点名

**现状**：我们的「起草消息」是**裸 `mailto:` 链接**（`draftLinks.ts`），点了直接甩给系统邮件客户端，**不弹任何应用内框**。
**她的**：`action-modal.tsx`（message/delegate 型）和人卡「发消息」都会弹一个**只读预览**弹层：收件人 chip + 主题 + 预写正文，出口是 邮件(mailto) / 聊天应用(复制到剪贴板) / 完成—加入待办。
**做（对齐 + 三处超过她）**：
1. 弹应用内草稿框：收件人 + 主题 + 正文
2. 🟢 **正文可编辑**（她是只读）——正文是 LLM 生成的，**不可编辑等于不可用**
3. 🟢 **「复制到聊天应用」为主出口**（国内团队在微信/飞书，mailto 基本是死路），mailto 保留为次出口
4. 🟢 **「完成」真写进跟进队列**——她的「加入待办」只弹一个 toast，不落库；我们有 `flowStore`，能真写
**不做**：Outlook / Google 日历深链（国内团队用不上）。
**验收**：点「起草消息」弹框 → 能改正文 → 复制成功 → 点完成后跟进队列真多一条（刷新仍在）。

### G7 议事室简化输出 · P0 · Danny 点名 · ⚠️ 新造，不是照抄

**先澄清一个前提**：Danny 原以为"她有我们没有"。**核实结果是两边都没有**——她的推理链（读取事实/交叉验证/匹配方法/生成动作）永远全展开，全库无任何折叠控件。所以这是**净新增**。

**现状（我们的问题）**：`LiteTerminal` 把每条流事件**逐行原样打**——`read_case` / `recall query=…` / 大段 `facts.md` 转储 / `cite` / `draft_advice`，**英文脚手架 + 中文事实混排**，`streamSource.applyEvent` 完全不过滤。对经理来说是一堵开发视角的墙。
**设计结论（来自差异清单）**：🟢 **她那 4 步手写轨迹，正好是我们简化视图该收敛成的形状**。她的是假的（1200ms 假延迟 + canned），我们的是真的（真 minimax + 真引用 `facts.md:NNN`）——**把真流事件映射进那四相，就是把她的皮套在我们的实质上**。
**做**：默认简化视图（四相叙事）；「展开原始流」可看完整事件流。
**注意**：最终建议卡和「Avery 的笔记」**已经是干净中文**——脏的只有实时思考流，别改错地方。
**验收**：默认视图里没有英文脚手架、没有 `facts.md` 转储；展开后原始流一行不少。

### G9 项目屏（整屏新建）+ 抽取粒度门 · P0

> 🔴 **这是差异清单里最大的结构缺口：我们根本没有项目屏。** 17 个真项目现在只能混在「你的团队」里当卡片。三家公司会上传项目文档，看不到项目屏说不过去。

**做**：独立项目屏（看板）。卡片含 标题 / 状态 / 负责人 / 到期 / 阻塞；点开进 `/projects/:id` 详情。
**🔴 必须设计「未知」态**（基于实测覆盖率）：

| 字段 | 覆盖 |
|---|---|
| title / summary | 17/17 |
| ownerId / ownerName | 16/17 |
| status / blockers | 13/17 |
| dueDate | **7/17** |
| progress | **6/17** |

进度和到期只有三分之一有值 —— **绝不能默认渲染成 0% 或空白**，那等于把"文档没说"错误呈现成"没有进展"。要显式显示「未知 / 文档未提及」。

**同属本条的前置：抽取粒度门。** handoff 挂着未修问题「项目粒度偏多（22–25 vs 应有 6），LLM 把里程碑当项目，无门」——我实测三亚 seed 抽出 **17 个**，正是这个病。**建项目屏之前必须先收敛粒度**，否则三家公司打开看到的是一地碎片。
**不做（本波）**：里程碑（我们无此数据）、成员历史时间线（无事件历史，她那份是 mock 造的）。
**验收**：三亚 seed 抽出的项目数落进合理区间（接近文档真实项目数，不是里程碑数）；无 `progress` 的项目显示「未知」而非 0%。

### G11 KPI 推导引擎（新工具 + 时间序列 + seed 补充）· P1

**Danny 拍板：算本波。** 且**不受 G10 那套红线闸限制**——那套闸只拦"人身上的打分键"，业务 KPI（营收/转化率）不沾，可独立开发。

**两头都缺，都要补**：
1. **缺工具**：`avery/tools.py` 全部工具只有 `read_case / recall / cite / draft_advice`，**没有任何聚合/计算工具**；全库 `kpi|metric` 只命中抽取路径。→ 新增一个 metrics/derive 工具：读原始条目 → 聚合 → **带出处**给出指标。
2. **缺原料**：单次 ingest 只有**一个时间点**，算不出环比/趋势/完成率节奏。→ 每次 ingest 存快照，建时间序列。
3. **缺测试素材**：见 §4 seed 补充。

**现实基线**：她 5 张 KPI 卡，我们目前只有「未解决差距」能真算，其余 4 张要等 1+2+3 齐。
**🔴 硬要求**：每个 KPI 必须能点开看"这个数是从哪几条算出来的"。做不到出处，就和她的硬编码假数据没区别。
**验收**：喂一份**只有明细、没有结论**的台账，Avery 能算出正确率值并给出算式。
