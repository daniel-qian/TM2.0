一 · 等你拍板（3 件）

这三件我都没有替你做。前两件会改变客户看到什么，第三件是个陷阱预警。

决策 1 · 最重 · 审计判为 blocker（3/3 票）

裸域名打开是 v01 冻结壳，八条线的成果客户一条都看不见

你昨天拍的是「v01 默认、v02 靠 ?v=2 手打」。那时 feat-050..060 还没合。现在合了，事实变了：路由化、会话不丢、统一 modal、账号体系、决策定级、议事室简化——全在 src/lite2 里，而客户拿到裸链接看到的是冻结的 v01。

更别扭的是深链：SPA rewrite 让 /followups、/team/xxx 都返回 200，但没带 ?v=2 就都落回 v01 的团队屏——路径对、内容不对。

我的建议：改成 v02 默认。代价是给 version.ts 加一个构建期 env（约十行，它现在写死 return '1'）。当初否掉这条的理由是「feat-051 一周内要改路由、现在做白做」——feat-051 已经落地了，那个理由没了。
如果你仍要 v01 默认，那 7-25 发给三家公司的链接就必须带 ?v=2，而且任何人转发时丢掉参数就会看到旧壳。
决策 2 · 后端要不要追平 main

后端现在停在 512b11d，是我刻意选的落后点

今晚我把后端从 07-17 的旧镜像换成了 512b11d 构建的新镜像，修掉了中文 id/去重/部门三个 blocker（见下）。选这个点是刻意的：它含中文修复链，不含 feat-053 的账号体系和迁移 0008——那条迁移从没往任何库 apply 过，把它带上生产是另一个量级的动作。

代价是后端比 main 落后两项：/auth/* 端点线上不存在；/team/{id} 不返回 feat-056 的 decisions[]。前端对后者已按 optional 处理（transport.ts 注释明写「老后端 pre-056 不发这个键」），所以不炸，只是那个功能在线上是空的。

⚠️ 07-19 上午更正：上面这段「落后两项」和下面原来那句「建议暂时不追平」，写的时候是对的，现在不对了。

对齐波在我写完之后又把四条数据真相级别的后端修复合进了 main，线上（512b11d）一条都没有。不是功能缺失，是产品会对客户说假话：

  • GB18030 静默销毁——中文 Windows 用 Excel 存的 CSV 被按 UTF-8 硬解成乱码，抽出 0 个人，却仍然回 HTTP 200 +「已读入 1 个文件」。我独立核过：512b11d 的 _parse_csv/_parse_text 仍是 data.decode("utf-8", errors="replace")；main 已换成带编码梯子的 decode_text。那就是国内 Excel 存 CSV 的默认编码，正对着 7-25 那批客户。
  • 「本月无法完成」读成 done，再被判「可推进」，理由写「项目自报已完成，且无风险信号」。（_NEG 在 main 里 12 处、线上 0 处）
  • 首屏摘要谎报「没有风险信号」，而同一份 payload 明明带着 blockers。
  • 非 ASCII token → 500（真 id 回 500、假 id 回 404），等于零凭据的存在性枚举 oracle，破 feat-038 那条红线。

好消息：有一条不碰数据库的路，我验过了。迁移 0008 的牵连是文件级的——_ensure_schema() 对 db/migrations/*.sql 全量执行，Dockerfile 又 COPY db/，所以任何 tree 里带着 0008 的镜像都会在第一个请求时无条件把它推进生产库。但只取 eval-harness/ 的 diff 是干净的（冲突全在前端）：

git checkout -b backend-subset 512b11d
git diff 6f838f3^ 6f838f3 -- eval-harness/ | git apply   # GB18030 + 413 人话上限
git diff d184b6c^ d184b6c -- eval-harness/ | git apply   # /advise 错误路径自己崩（NameError）
# → tree 里没有 0008，数据库一个字节都不动
cd eval-harness && AVERY_BRAIN=stub python -m pytest \
  tests/test_file_truth_encoding.py tests/test_advise_brain_config_error.py -q
# → 30 passed in 2.47s（已实跑，无 LLM 开销）

改后的建议：追平，但只追这个子集。fixA/fixC/fixD 的 diff 依赖中间提交，要补得再挑一轮。建不建、什么时候建仍然是你的闸——我没碰线上任何东西。

决策 3 · 一个 30 秒就能踩的坑

别把 Supabase 的两个 key 贴进 Vercel

审计单独把这条拎出来（SKEW-03，major，3/3 票）。VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY 现在没配，所以登录入口不渲染，游客路径干净——这个状态是对的。

但它看起来像「就差这一步」。一旦有人（包括未来的我）在面板上把这两个值贴进去，前端会立刻长出登录 UI，而后端没有任何 /auth/* 端点（决策 2），迁移 0008 也没 apply。结果是一个点了就 404 的登录框，出现在发给真客户的网址上。

收工前拆掉了这个陷阱的第二层。feat-053 的认证面上还剩两处裸 fetch（fetchAccountContexts / claimContext），绕开了错误文案那层，抛的是 account claim HTTP 401 这种开发者串——正是今晚修的那个中文缺陷本身，只是躲在登录开关背后。今天打不到，配上 env 的那一刻就可达。已改走统一的错误层，全仓再无这种裸抛。

顺序是：先后端追平 + apply 迁移，最后才配这两个 env。反过来做，中间那段时间线上就是坏的。

其二：我提交过一次带冲突标记的代码

凌晨合 main 时，我把验证和提交写成了一条链：

npm run typecheck 2>&1 | tail -2 && git add -A && git commit …

&& 取的是管道最后一环 tail 的退出码，不是 tsc 的。于是 typecheck 明明报了 TS1185: Merge conflict marker encountered，链条照走，把还带着 <<<<<<< 的 draftLinks.ts 提交了进去。

下一步改用 npm run typecheck > log 2>&1; echo exit=$? 单独取真退出码，当场发现，该提交未推送，已 --amend 修正并把三处冲突逐一解掉（其中一处是真实的类型冲突：feat-058 把 mailto 路径换成了应用内草稿框，我那个函数已被取代）。

教训比这次的后果重要：把闸门写进管道，闸门就形同虚设。本仓的验证命令以后都单独跑、单独取退出码。

中文是 MiniMax 过一轮、我定稿的——驳回了一条

M3 把 404 那句改成「访问凭据失效，公司数据仍在，请重新登录」。线上根本没有登录（Supabase 未配、登录入口不渲染），那是让用户去做一件做不到的事。定稿保留：「这台浏览器的访问凭据没了 —— 公司数据还在，只是这台浏览器打不开它了。」
