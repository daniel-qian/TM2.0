## 1 · RLS 是什么，以及它为什么不在这条路上

RLS（Row Level Security，行级安全）是 Postgres 自带的功能：给表定一条规则，数据库自己按行过滤，
比如「每个用户只看得到 user_id 等于自己的行」。

它是**为「浏览器直连数据库」那种架构准备的**。Supabase 的典型用法是前端拿 anon key 直接
`select * from projects`——请求根本不经过你自己的服务器，那时唯一能拦住 A 读到 B 的就是 RLS。

**Avery 不是这个架构**（`src/lite2/auth/supabaseClient.ts` 实证：前端那个 Supabase 客户端只用来
登录，全仓零 `.from()` / 零 `.rpc()`）。所有数据都过我们自己的后端，后端持有数据库口令，
每一次读写都过 `ingest_api.authorize_context()` 那**一道**门。所以 RLS 在这里不是「没做」，
是**不在这条路上**——门在后端。补充：`avery` schema 没暴露给 anon key（既有结论，
`supabase-avery-schema-not-exposed`），拿 bundle 里的 anon key 打 Supabase REST 也够不着我们的表。

**RLS 不是政策也不是合规要求，是个技术手段**，所以「简单密码符不符合 RLS 政策」这个问题不成立。
但底下那个担心是对的，见 §2.3。

### 隔离的真实形状（复核过的事实）

| 层 | 机制 | 出处 |
|---|---|---|
| 谁能读一份档案 | `authorize_context()`：**两把钥匙**——owner_token（不可猜密钥，浏览器存 localStorage）**或** 已验证的 Supabase 用户 + `avery.account_contexts` 里查得到 | `ingest_api.py:141-173` |
| 失败长什么样 | 与「这个 id 不存在」**逐字相同的 404**，无存在性 oracle；常数时间比较 | 同上 + #94 判据⑦ 生产实测 |
| 数据怎么分家 | 每张表都 `context_id NOT NULL REFERENCES avery.contexts ON DELETE CASCADE`——一家公司的全部数据物理上是一棵子树 | 迁移 0002/0005/0008/0012/0013 |
| 「两个账号不串」 | `account_contexts` 上 **context_id 唯一索引**——一个档案至多属于一个账号，**数据库层拦**，不是应用层判断 | `0008_account_contexts.sql:40` |

**localStorage 不是那道门**，它只是浏览器放第一把钥匙的抽屉（性质同 cookie）。

## 2 · 账号分发

### 2.1 Supabase 后台能做什么、不能做什么

| 动作 | 能否 | 说明 |

| 建号 | ✅ | Authentication → Users → Add user，勾自动确认。**#94 那两步（signup API + SSH 进库 UPDATE email_confirmed_at）可以合并成一步** |
| 删号 | ✅ | |

| **读密码** | ❌ | 库里是哈希。**任何人任何时候都读不出原文** |

🔴 **这条改变了「复制粘贴发给别人」的可行性**：密码**只在你创建它的那一刻存在一次**，
没记下来就永远没了（只能重设）。所以 Supabase 后台可以是账号的**管理处**，但**当不了密码的档案柜**——
仍然需要一份你自己控制的记录（密码管理器最好）。这也正面回答了「别放 C 盘临时目录」：
问题不是路径，是**得有一个持久的、你自己的地方**。

### 2.4 冻结注册门（同意，而且不止一处）

三层，缺一不可：

1. **Supabase 后台关掉 signup**——**这是唯一真闸**。不关的话，任何人拿 bundle 里的 anon key
   直接调注册接口就绕过了你的界面。
2. **前端撤掉注册入口**（`AuthPanel.tsx:210` 的 signin/signup 切换）。
3. **顺带把那句假话收掉**：#94 逮到的「已注册邮箱再点注册 → 200 + 假成功」，

## 3 · owner_token 那个洞（Danny 问的「堵①」）

**事实**（#94 判据⑤ 生产实测）：档案被账号认领之后、用户登出之后，旧的 owner_token 照样能读。
`authorize_context` 是**或**的关系，两把钥匙谁都行，而 token 这把**发出去就收不回**。

**风险面**：谁的浏览器曾经存过那串 token，谁就永久有一把钥匙。演示机、共享电脑、
借出去点过一次的笔记本——都留了钥匙。

**修法**：**认领的那一刻轮换 owner_token**。此时用户已登录，账号那条腿接得住他自己，
旧 token 当场作废。改动面小（`/account/claim` 一处铸新 token + 回给当前浏览器）。

⚠ 副作用要想清楚：如果同一个人在另一台设备上正靠旧 token 用着同一份档案，轮换会把那台踢掉。
对「一家公司一个账号」的用法这是**想要的行为**；要写进票面而不是当意外。

## 4 · 🔴 探索中挖到的：抽取期间的丢失更新（今天就在丢数据）

Danny 说「共用登录也行，只要能互不影响就行」。去读并发这块，发现的问题**比共用登录更早、
一个人用也会中**。

### 4.1 机制

补传（appendFiles）的整条路是：

```
reg.get(context_id)          ← file_append.py:136   读出整个档案（快照）
    ↓
extract_docs(...)            ← file_append.py:~183  模型读文件，真 LLM 两三分钟
    ↓
reg.put(ctx)                 ← file_append.py:272   把整个档案**整份覆盖**写回
```

`put()` 是**快照替换**语义（`file_append.py:9-10` 自陈）。而 `avery.contexts` 表上
**没有版本列、没有乐观锁**（迁移 0002 实证：只有 created_at / updated_at）。

于是：

| 时刻 | 发生什么 |
|---|---|
| 10:00:00 | 经理点上传 → worker 读出档案（快照 A） |
| 10:00:30 | 经理等得无聊，改了一张卡的负责人 → **真的存进去了**（自己的 get→改→put） |
| 10:02:00 | 模型读完 → worker 写回「快照 A + 新文件」→ **10:00:30 那个改动没了** |

屏幕上没有任何提示，也不会闪回旧值——**要到下次刷新页面才发现改动不见了**。

### 4.2 四个加重的点

1. **界面不挡**：卡片的编辑/归档按钮绑的是 `projectWriteBusy`（它自己保存时的短暂禁用），
   全仓只有 `UploadPanel.tsx:122` 与 `OnboardGate.tsx:317` 两处看 `ingesting`——
   **没有任何一处把「抽取中」与「手动编辑」互斥**。
2. **共用登录会放大**：B 在另一台电脑改卡片时，A 这边正在上传；B 完全不知道，本地也挡不住。
3. **离线测试结构性测不出来**：内存腿 `get()` 返活对象（两边改同一个东西，丢不了），
   pg 腿返快照副本。既有的碑（`offline-suite-blind-to-pg-persistence`）正是这一条——
   这类 bug 在 4217 条离线测试里 **100% 全绿**。
4. **压测也够不着**：`test_e2e_stress.py` 那 8 路并发**各建各的 context**
   （`created.append(r.json()["context_id"])`），**从来没有两个写者打同一份档案**。

搜过全仓：`并发写` / `lost update` / `last-write-wins` 零命中——**这不是已知取舍，是暗区**。

### 4.3 修法（由轻到重）

1. **让贵的那段不持有档案**（主修）：`extract_docs(fresh_docs, extractor=extractor)`
   **只吃新文档、不吃 ctx**——抽取根本不需要档案，只有归并需要。顺序改成
   「先抽取 → 再 `get()` → 归并 → 立刻 `put()`」，窗口从两三分钟缩到几毫秒。
   ⚠ 136 那次 `get()` 还供着幂等 key 检查等前置，拆的时候要分清哪些必须在前。
2. **档案加版本号 + 写回时 compare-and-swap**（durable 层）：对不上就重读重并。
   这一层的价值是**让未来任何一个长窗口当场报错，而不是静默吞掉**。
3. 判据必须落在 **needs_db** 上（见 4.2③，离线腿测不出来），且要有**对照基准**：
   不修的代码在同一场景下必须真的丢（born-red），否则这门是空真。

## 5 · 共用登录：结论

Danny 的用法（一家公司一个账号，几个人共用）在**修掉 §4 之后**是成立的。逐条：

| 场景 | 今天 | 修 §4 后 |
|---|---|---|
| 两个人同时上传 | ✅ 安全（worker 单线程串行认领，`FOR UPDATE SKIP LOCKED`） | ✅ |
| 一个人传、另一个人改卡 | 🔴 改动被静默抹掉 | ✅ |
| 两个人同时改不同的卡 | 🟠 窗口毫秒级，但输的一方是**整份档案**回退，不是丢一格 | ✅（要第 2 层才彻底） |
| 一个人在 A 机传、B 机看 | ✅ 看得到（轮询/刷新） | ✅ |

**仍然留着、但可接受**：一个账号名下有多份档案时，登录只自动打开**最新那份**
（后端 `ORDER BY created_at DESC`、前端取 `[0]`），界面上今天没有切换入口（#88 单档案模型收口）。
→ 「一家公司一个账号」是对的用法；一个账号塞两家公司会看不见旧的那家。
