## 1 · 诊断（量到的，不是读码推断的）

### 1.1 对话侧栏「丢失风格」——四条病根

| # | 病 | 量到的事实 |
|---|---|---|
| ① | **栏读成一张浮在页面上的白卡片** | 栏底色 `rgb(255,253,248)` **比暖纸画布更亮**；上沿从 `--lite2-clear-top`(96px) 起、下沿停在 `max(120, footer+76)`——**上下各一道悬空截断边**。参照物（Claude / 访达 / Notion）的边栏一律比正文区**暗**一档且**贴边通到底**。这条是"没上皮肤"最主要的来源。 |
| ② | **一场占两行 ≈ 85px** | 标题行 + 左右分栏的 meta 行。1440×900 的屏上只装得下 9 场。Claude 是**单行 ~34px**。同一块地方能装 12+ 场。 |
| ③ | **meta 行几乎全是噪声** | 播了 9 场，其中 8 场的 meta 文字逐字相同（「单独问过一次」）。满行的墨、零信息。 |
| ④ | **每行三个对齐点** | 标题左对齐 + meta 左 + 时刻右（`justify-between`）。列表因此没有一条稳定的竖轴，眼睛横着走。 |

附带：「新对话」是一枚描边胶囊，长得像表单控件不像本栏主动作；静息态无 hover/选中提示；无图标、无分隔。

> ⚠ 一条**不是 bug** 的观察，免得下一个人误报：我播的 9 条 `advise_runs` 里 `seq`（插入序）
> 与 `created_at`（我手写的时刻）刻意不一致，于是屏上「今天」组内看着是旧→新。后端排序键是
> `seq`，真实使用里两者恒一致。**这是我造数据的产物，不是排序 bug。**

### 1.2 资料库 layout——四条病根

| # | 病 | 量到的事实 |
|---|---|---|
| ① | **两条互不相干的左边界** | 内容列 `min(100%, 820px)` 吊在视口正中 → 1440px 下两侧各 ~310px 死白；而顶栏胶囊是**左对齐**的。Danny 说的「两侧大片空白」就是这个。 |
| ② | **四件事垂直摞成一根长条** | 文件 / 常驻表单 / 给这家公司补资料 / 新建一家公司，全部默认摊开，桌面满数据态 ~2700px。 |
| ③ | **视觉权重与使用频率完全倒挂** | 最罕用的「新建一家公司」占着全页**最重的一张白卡片**（内含整套上传家具：dropzone + 格式说明 + 隐私句 + 两条链接）；天天要看的「谁交了」压在 ④ 段最底。 |
| ④ | **文件行是 flex-wrap 的汤** | 手机 390px 上 9 行出现 **4 种高度、3 种内部顺序**——名字长短决定折行位置。这是「好乱」最实的一处，也是最好修的一处。 |

附带：`排序` 是一枚**原生未上样式的 `<select>`**（带系统箭头）；「当前资料」+「你的文件」双标题说同一件事。

## 2 · 提案

### 2.1 一条贯穿两块屏的主张

**把「垂直摞」换成「左右分」，并给导航栏一套统一的视觉语言。**

两块屏共用同一根栏的规格（同宽度节奏、同行高、同 hover/选中语法），于是「侧栏」不再是对话页
一个孤零零的部件，而是这个应用的**壳**。这也是"上了皮肤"最省事的做法：一套规格，两处消费。

### 2.2 导航栏视觉规格（共用）

| 项 | 值 | 为什么 |
|---|---|---|
| 底色 | `rgba(--lite2-ink-rgb, 0.035)` | **下陷**而非凸起。这一条单独就修掉「白卡片」观感的一大半 |
| 上下沿 | `top: 0; bottom: 0`（贴边通到底） | 消灭两道悬空截断边；顶栏胶囊浮在其上（Linear/Notion 同款） |
| 右界 | `1px solid var(--rule)` | 一根硬线，不用阴影 |
| 行高 | `min-height: 34px`，`padding: 0 10px`，`radius 8px` | 单行；密度对齐 Claude |
| hover | `rgba(ink, 0.05)` | |
| 选中 | `rgba(accent, 0.13)` + **2px accent 左封条** + 600 字重 | 左封条是"当前"最省墨的说法；accent 语法抄既有 `.lite-ref-chip`，**不新开色阶** |
| 组标 | 11px / 700 / **`--ink-soft`** | 🔴 不吃 `--ink-faint`：11px 的 faint 在 paper 上只有 ~4.7:1，AA 余量 0.2，aurora 更薄。#80 已立此碑 |
| 宽 | 对话 264px（**不动**）· 资料库 208px | 264 是「发问零跳变」判据的锚，动它等于自找间歇假红 |

### 2.3 对话页

1. **会话行收成单行**。轮数只在 >1 时才占墨（多轮才是有信息的那一半）；**时刻整条从静息态撤掉**，
   只在 hover 时替补出现——日期组标已经说了是哪一天。
   ⚠ `data-history-thread` / `data-history-turns` 两个属性**照旧挂在 button 上**，
   verify-room-threads 的 5 条属性判据零改判；撤掉的只是可见文本。
2. **「新对话」并入行的节奏**（同 34px / 同 padding / 同圆角），用 accent 文字色拎出来但**不做实底**——
   实底会把视觉重心永久钉在栏顶，而经理真要点的是下面那些会话。
3. **开场块在「顶栏以下、composer 以上」那块矩形里垂直居中**，吃掉现在那 ~700px 虚无。
   🔴 **composer 几何一个字节不动**：`verify-room-claude-rework` 的「发问零跳变」逐像素比对
   composer 的 x/y/宽在第一问前后是否一致。把 composer 一起收进来居中 = 正中那条判据，
   也正是 #75 花一整票消灭的那类病根。（我第一版原型就是这么画的，自己拍出来才发现，已改。）

### 2.4 资料库 → 两栏 file explorer

```
┌──────────────┬──────────────────────────────────────────────────┐
│ 资料库        │ 文件   9 份 · 共 18.8 KB · 212 处可引用片段        │
│              │ ┌──────────────────────────────────────────────┐ │
│ ▸ 文件     9 │ │ [↑ 上传文件] [在这些文件里找…]  [排序▾] [刷新] │ │
│   常驻表单  1 │ └──────────────────────────────────────────────┘ │
│              │  文件名          大小  可引用片段  上传时间  状态   │
│              │  ──────────────────────────────────────────────  │
│              │  📄 八月排班表.xlsx — 正在逐页通读，已用时 42 秒  │
│              │  📄 公司概况与部门手册.md  2.2KB  18  08-10  ●已读取│
│              │  …（hover 才现 下载/删除，但格子恒占位不推挤）      │
│ ──────────── │                                                  │
│ 🗑 清空这份档案…│  ┌ 把文件拖到这块工作台的任意位置就能加进来 ┐      │
└──────────────┴──────────────────────────────────────────────────┘
```

> 栏底那一条是**销毁类**动作（Danny 拍板：没有「新建」，只有「清空这一份」）。
> 静息态不用红——常驻的红会把整根栏染成警告区；红只在 hover 出现，点下去还有一道硬确认。
> ⚠ `knownContexts`（「这台电脑上传过的几批」）在单档案模型下是**余数**：存量用户机器上
> 可能已经有好几份，直接砍掉＝那些档案再也回不去（数据还在后端、入口没了）。
> 倾向**保留为只读的「历史档案」入口、不再产生新的**——这一条我没有拍板权，单独摆给 Danny。

1. **左栏＝分区**（文件 / 常驻表单），把纵向长条换成横向切换。~2700px 的滚动就此消失。
2. **上传口长在文件工作台的工具条上**（`↑ 上传文件` 主钮 + 整块工作台接拖放）——
   Danny 要的「上传窗口和它放在一起」。现状那两个长得几乎一样、方向却相反的 dropzone 收成一个。
3. **真列，不是 flex 汤**：`grid-template-columns` 钉死列宽 → 名字长短再也改变不了行的结构。
   这是手机那锅汤的**根治法**。数字列一律 `tabular-nums` + 右对齐。
4. **表格有阅读上限 1120px**（工作台本身占满）：撑满 1440 会让文件名与数字列拉开近 900px 空档，
   眼睛得横着走一整屏。"整页只用中间 820px"的解法不是"什么都撑满"。
5. **上传进度就长在表格顶端的那一行**里——上传的东西最终会变成这张表的一行，
   进度就不该另开一块面板。（仍无百分比：`/ingest` 不吐进度信号，假进度条会卡 90%。）
6. **`排序` 换成自绘控件**，原生 `<select>` 是"没上皮肤"在这块屏上最刺眼的一处。
7. **双标题收成一层**：页头一行说清「这是什么 + 有多少」。
8. **常驻表单区内部重排**：「谁交了」提到**最上**（天天看），铸链在中（一周一次），
   拼装器收进「改表」（很少动）。这一条是纯顺序调整，零新部件。

### 2.5 手机（≤860）

- 导航栏退化为抽屉，开关钮继承 `data-history-toggle`（门的 driver 抓手必须留在 DOM 上）。
- 文件行退化为**结构固定的两行**：第一行文件名，第二行 meta，动作收进行尾溢出菜单——
  **不允许 flex-wrap 自由折行**（那正是现在这锅汤的成因）。
- ⚠ 手机抽屉态在**所有既有门里零覆盖**（四道门的视口都硬钉 ≥900）。本轮要补，别当它验过。

## 4 · 任务书另外两条的回执

### 4.1 W33「链接过期了」——**不是产品 bug**，两条假设都不成立

- **假设②（自动铸链抄了旧 `expires_at`）证伪**：`avery/ingest/form_autofill.py:179,187-193`，
  `created = now_iso()` + `expires_at=default_expiry(created)`，**当场算**。从上期抄过来的只有名册，
  经 `_recipients_of`(:100-114) 投影成 `_Recipient{person_id, person_name, project_ref}` 三个字段——
  **结构上装不下** `expires_at`。手工铸链路径（`form_api.py:230,238`）逐字相同。
- **假设①（示例种子带旧日期）也证伪**：`tests/fixtures/demo-seed/` 里只有 9 份 `.md`，
  `service/demo.py` 全文无 `form`/`submission`/`expires_at`。表单行只可能由那两条铸链路径产生。
- **真正的解释**：`expired` ⟺ 未提交 且 库里存的 `expires_at` 真在过去（`form.py:209-224`）。
  只有两种东西能造出它——**(a) 撤回**（`form_api.py:391` 把到期拨到此刻，这是设计，T9 门就断言这个渲染）；
  **(b) 演习夹具用显式 `period` 铸行**（如 `verify-forms-proactive.mjs:60` 硬写 `'2026-W01'`），
  行的**周标签与真实铸造时刻脱钩**，放在共用库里过几天就成了"刚铸就过期"的样子。产品 UI 从不发 `period`。
- 2026-08-10 正是 **W33 的周一**，走产品路径在 W33 铸的行 `expires_at ≥ 08-17`，**不可能过期**。
- ⚠ **现场已不可复现**：`rehearsal0808` 今天被重建，`avery.form_submissions` **0 行**，
  截图那批数据没了。所以我只能给代码级定论 + #82 的时间旅行台架佐证（+0d…+365d 全绿），
  **拿不到那四行的 `expires_at` 实物**。要百分百钉死，得在下次复现时立刻跑：
  `select person_name, created_at, expires_at, submitted_at from avery.form_submissions where period='2026-W33';`
- **不修产品**。真要修的是**夹具卫生**（`verify-forms-proactive.mjs:60` 那种脱钩周标签），属独立小票。
- 顺带一个真空洞：**没有任何测试断言自动铸链的 `expires_at` 数值**（只断言 `status=='open'`）。
  在 `tests/test_form_autofill_t9.py:569` 旁边补一句 `expires_at - created_at == 7 days` 很便宜。

## 5 · 两条产品拍板项 —— Danny 0810 已拍板

### 5.1 A ·「新建一家公司」——**整个概念取消**

Danny 原话：

> 不要有"新建"的想法，这完全不符合设计思路，可以让用户自行删除已经上传的过期/错误文件？
> 并且自动更新数据库？可以有完全重建的选项，但是不是新的，而是直接清空，要有很硬的确认引导。

🔴 **这比我提的方案（藏起来+改名）更彻底，也更对。** 我原提案还留着"另一份档案"的心智，
Danny 要的是**一个人从头到尾就一份档案**：

| | 旧心智（现状） | 新心智（拍板） |
|---|---|---|
| 传错了一份文件 | 没法删 → 只能整库重开 → **多出一家公司** | **删掉那一份**，库跟着自动更新 |
| 想从头来 | 「新建一家公司」= 再开一份，旧的还在 | **清空这一份**（`context_id` / `owner_token` 不变），走硬确认 |
| 档案数量 | 1..N，靠 `lite2:knownContexts:v1` 名册回得去 | **恒 1** |

落地要点：
1. **删单份文件必须"自动更新数据库"**——不能只是清单上少一行、而那份文件推导出来的
   负责人/进度/负荷还留在卡片上。这是这条拍板里**技术风险最高的一句**，正在核实。
2. **「清空这份档案」是销毁类动作**：按 AGENTS.md 的闸，硬确认（建议"输入店名才放行"这一档）。
   静息态不用红——常驻的红会把整根栏染成警告区；红只在 hover 时出现。
3. **`mode='new'` 的上传口从 UI 撤掉**。⚠ 但它同时是**全新用户的第一次上传路径**，
   不能连根拔——正在核实哪些消费者还挂在它上面。
4. ⚠ **`knownContexts` 名册怎么办**是这条拍板的余数：存量用户机器上可能已经有好几份。
   直接砍掉 = 那些档案再也回不去（数据还在后端，但入口没了）。倾向：**保留为"历史档案"
   的只读入口、不再产生新的**。这一条我没有拍板权，会单独摆事实给 Danny。

### 5.2 B ·「自动更新 + 已查阅/撤回」——**完整做**

Danny 选了最重的一档：清单 + 逐条「已查阅 / 撤回」。

我在选项里标了"撤回要求可反向回滚、是独立大工程"，Danny 仍然选它——**说明这是产品的核心叙事，
不是锦上添花**（Avery 敢自动改你的数据，前提是你能一键把它改回去；没有撤回，"自动"就是不可信的）。

因此排期上**它不该塞进这轮布局重做**，而应是**紧接着的一条独立主线**。正在核实：
- 现有 `conflicts`（差距卡的后台）是不是已经是 `{旧值, 新值, 两边出处}` 的记录——若是，
  changelog 的数据模型 80% 已经在了，是顺着长而不是新起炉灶；
- 每个推导字段是否已带出处（demo payload 里见到 `{"value":70,"caliber":"本人自述","source":"本周周报.md:11"}`，
  若这种 provenance 是普遍的，它就是 changelog + 撤回共同的骨架）；
- 撤回一条改动到底要不要新表/迁移。

## 6 · A 条可行性回执 —— **「并且自动更新数据库」今天做不到，而且它是新模型的拦路石**

### 6.1 最要紧的一条：删文件**不会**收回它推导出来的结论

`avery/ingest/file_delete.py:65` 的 `delete_document_from_context` 只动**四个列表**
（`materials` / `signals` / `granularity` / `conflicts`，:100-112），**从不碰**
`ctx.extraction.people` 与 `ctx.extraction.projects`。

这不是疏忽，是 #77 票内的明文裁定（`file_delete.py:27-33`）：

> **不删**：人卡 / 项目卡 / 方法卡。不是偷懒，是**血缘不够**：`PersonEntity`/`ProjectEntity`
> 只有实体级单值 `source`，且归并是 keep-first …… 这是**诚实的降级**

而且有测试钉着（`tests/test_file_delete_t77.py:177` `test_delete_keeps_the_person_cards`）。

**照你的场景走一遍**：删掉《旺季排班协调纪要.md》之后——
- 原话「宴会部小马接手婚宴对接」从 `facts.md` 里没了 ✅
- 但项目卡上 `owner: 小马` **还在**，`materialize_memory` 每次重建 `facts.md` 时
  还会把 `Project '婚宴对接' (owner: 小马)` 重新写进去（`registry.py:1434-1461` +
  `extract.py:353-356`），**顾问仍然会引用它** ❌

🔴 **在旧模型下这只是"诚实的降级"，在你拍板的新模型下它是硬伤**：以前抽取错了还能
「新建一家公司」洗掉重来，现在那个出口被你砍了——**删文件成了唯一的纠错手段，而它纠不干净**。
`file_delete.py:33` 自己点名了前置条件：「要真做『卡随文档收缩』，前置是给实体加**来源文档集合**」。

**结论：实体血缘（给 `PersonEntity`/`ProjectEntity` 加来源文档集合 + 改归并路径）
不是可选的后续票，是新数据模型的第一块地基。**

### 6.2 「清空这份档案」——比逐份删**更容易**

反直觉但成立：清空不需要血缘。**每一个实体都来自某份文件，全清一定是对的**，
所以它绕开了 6.1 那道坎。可以先落，作为纠错的兜底出口。

两条要纠正的既有认知：
- `delete()` 是 **pg 独有 + context 级**（`pg_registry.py:1250`），删的是 `contexts` 行本身，
  `context_id`/`owner_token` 跟着没——**正好是「清空但留档案」的反面**，不能复用。
- `test_registry_protocol.py:89-97` 不只钉住 `"delete"` 这个名字，它**明令禁止**内存腿长出
  `delete()`（`assert not hasattr(ContextRegistry, "delete")`）。新方法得换个名字（如 `empty_context`）。
- `clear()` 两条腿都有且在 Protocol 里，但语义是**清掉进程/库里所有 context**——别有人拿它凑数。

成本 ≈ 12 个文件：Protocol + 两条 registry 腿 + 新路由 + 两份测试（含 `@needs_db`——
`test_registry_contract.py` 离线被 deselect，pg 腿的洞会绿着上线）+ transport + store
（`adoptContext` / `resetLiteCompanyData` 两抄本要锁步）+ 硬确认 UI + 中英两份文案 + 一道新门。

**保留清单**（清空文件时**不该**一起没的）：对话历史 `advise_runs`、常驻表单模板、
**员工已交的答卷 `form_submissions`**（那是别人的话，且外面还有活链接）、`asks`、
账号归属 `account_contexts`、`owner_token`。⚠ 一个雷：留着 submissions 就意味着
`POST /team/{id}/forms/{sub}/ingest`（`form_api.py:750`）之后还能把实体重新灌回来——
"清空"不会自己保持为空。

### 6.3 撤掉「新建一家公司」不止改一屏

`uploadFiles`（新铸 context 的那条 `POST /ingest`）有**四个调用点**，其中两个不能碰：
- `OnboardGate.tsx:309`——**全新用户的第一次上传**，档案就是这么铸出来的；
- `HomeScreen.tsx:373`——首页骨架的上传卡，`HomeScreen.tsx:368` 记着一条**你自己的拍板**：
  「首访者的第一个动作不该先跳一屏」。

正解形状：`uploadFiles` 降级为**只在 `contextId === null` 时开火的引导路径**，
其余一律走 `appendFiles`；`UploadPanel` 的 `mode` 由 contextId 推导、不再由调用方传。
⚠ 两条状态机（`newCompanyStatus` vs `appendStatus`）**不能天真合并**——
`notifyStore` 靠 `ingesting→ready` 这个跃迁合成「团队已就绪」通知，合并了会**每次补料都误报**。

门账：`verify-context-switch` **15 条整条报废**（它的前提就是"两个 context"）·
`verify-append-story` 19 条里 **②（:119-121）必红**（它显式要求屏上存在 `data-upload-mode="new"`）·
**`verify-files-ia`**（17 条，任务书没点名的第三道门）③ 必红（它断言 `files-forms` 排在 `files-new` 前面）。
🔴 一个假绿陷阱：`verify-context-switch` ⑥ 的两条**源码级**判据（`forgetContext` 不许出现在
`catch` 里）在函数被删掉之后会**静默变绿**，不是红——改判时要主动退役，别等它报警。

i18n：`i18n-orphans` 当前**基线 0 孤儿**，所以一砍就看得见。会孤儿 **13 个键**
（`upload.again*` / `upload.switch*` 共 12 + `lite2.filesUploadTitle`）。
另有两条会**从孤儿变成撒谎**：`againTitle`「从这里上传会新建一家公司」——留着改用途就是假话。

## 7 · B 条可行性回执 —— 前半便宜得出乎意料，后半是一场战役

### 7.0 🔴 先拦一条：**做这个等于推翻 3 天前的拍板③**

`.issues/gap2-0807/tickets.md` 拍板③（2026-08-07，你自己拍的）：

> 补传后的吵闹度 = **安静更新**：旧读数被新资料顶掉时卡片直接显新值、出处指新资料，**不打扰**；
> 只有互相矛盾/新的更糟才上今天页

`file_append.py:23-32` 是照着它刻的注释。B 条要的正好相反——**每次自动更新都主动报告**。
两条都是你说的，间隔三天。我不替你选，但**不能装作没看见就动手**。
**✅ 2026-08-10 已定**：按「两者共存」落——自动更新做成**不打扰的事后流水**：
**不弹通知、不占今天页**，只在资料库里有一处可查。拍板③ 防的是"每次补料都弹一堆通知"，
B 要的是"事后查得到、能撤回"，这个形状两条都满足。（Danny 审方案时未推翻此读法。）

### 7.1 前半（只读清单）——**几乎白送**

两个现成件比预想的好：

1. **`provenance[field].origin === 'doc'` 恰好标出「被后来的上传顶掉过」的那些格子。**
   `PersonEntity.provenance` / `ProjectEntity.provenance`（`extract.py:196,339`）只在
   **补传 / 手编 / 表单回流**三处 stamp——首次 `/ingest` 一个都不写。所以 `origin:'doc'`
   出现的地方**精确等于**"这个读数被一份更新的资料改过"。`source` 就是引文、`updated_at` 就是时间。
   `team_cards()`/`project_cards()` 已经把它透传到前端（`teamData.ts:221` / `projectView.ts:195`）。
2. **「已查阅」的交互层已经建好了。** `flowStore.ts:47,154-165,247-260` 是三态
   （resolved / dismissed / 未标）localStorage 标记库，**今天页的冲突卡已经在用它**
   （`conflict_` 前缀，`HomeScreen.tsx:1043-1048`），`restoreGap` 就是取消标记。零新状态机。

缺的只有三样，都不大：
- **旧值**（"从 X 改成 Y" 的前一半）只在 `conflicts` 里有，而 `conflicts` **不在 `/team` payload 里**。
  最便宜的补法：加一个 additive 的 `payload["conflicts"]`（`_team_payload` 已有四条 additive key 先例），
  纯投影、零 schema 改动。
- **新建的卡不会出现**：`merge_person_reading` / `merge_project_reading` 追加新实体时**不调 stamp**，
  新人/新项目的 provenance 是空的。
- 若「从 X 改成 Y」对**全部 10 个字段**都是硬要求，那前半就继承了后半的记录工作、不再便宜。

**结论：只读清单是一张前端票 + 一个 additive payload key。可以搭这轮布局一起做。**

### 7.2 后半（逐条撤回）——**大，而且原因只有一句话**

**旧值在 `extract.py:2344` 被 `setattr` 抹掉了，只有 3/10 的字段留得下来。**

```python
if fname == "ownerName": cur.ownerId = ""
setattr(cur, fname, new)
self.stamp(cur, fname, ...)      # ← 连旧的 provenance 记录也一并覆盖
```

无历史表、无 journal、无版本；`reg.put()` 是 DELETE+INSERT 整快照替换。
唯一留住旧值的是 `note_conflict`，但它被 `_CONFLICT_FIELD_ALLOWLIST` 卡死：

| 类 | 补传可覆盖的字段 | 留得下旧值的 |
|---|---|---|
| person | `role` / **`team`** / `tenure` | 1/3 |
| project | `ownerName` / **`status`** / **`dueDate`** / `summary` / `progress` / `risk` / `milestones` | 2/7 |

**10 个里 7 个的旧值今天无处可寻。** 撤回没法建在现状之上——第一步不是 UI，是让 absorb
**先把它要毁掉的东西记下来**；而且**存量公司永远拿不到追溯撤回**。

存哪儿（顺带订正一条我们自己的规矩）：
- ✅ **嵌进 `provenance` 里免迁移**（如 `{origin, source, updated_at, prev:{...}, batch_id}`）——
  `entities.payload` 是 jsonb，`0009` 的 CHECK **只查顶层键**，加嵌套键不加顶层键。
- 🔴 但**给 `PersonEntity` 加一个顶层 dataclass 字段就必须动迁移**：`0009` 钉死字段清单，
  `test_registry_contract.py:882` 一加字段就红，且迁移头写着「就地改数组、不许叠新迁移」。
- 新实体 kind（journal）走 `0010` + `_ENTITY_KINDS` 就地改两处常量，`conflict` 就是先例。

真正贵的不是写回旧值（`patch_manual_*` 已建好，且 ADR-0028 的"手编赢"让撤回**粘得住**），
而是那一次 `absorb()` 顺手干的别的事：**冲突记录要retract 并重选胜者**（`file_delete.py` 头
明说这等于"替抽取器编一个它从没做过的判断"，需要产品拍板）· **`ownerName` 撤回不是一个字段**
（`ownerId` 被清空后由 `_link_owners` 重连，光写回名字信号还挂在错的人身上）·
**列表并集字段被 `[:6]` 截断过、第 7 项起原则上不可恢复**（UI 就不该给这些字段撤回钮）·
`facts.md` 必须重materialize，否则顾问还在引用被撤回的值。

**量级：T10 级别的一场战役**（T10 是 45 条新后端测试 + 18 条变异 + 4 条 `@needs_db`）。

### 7.3 订正两条我给侦察的错误前提

- **`gapDerive.ts` 不消费 conflicts**——它是纯客户端启发式，只看 `statusRaw` + `blockers`。
  冲突卡与差距卡是同屏的**两张不同的卡**。真链路是
  `conflicts → decision_cards()/briefing() → decision_grading.py → payload["decisions"]`。
- **冲突到前端时已经不是记录、是字符串**（`_conflict_evidence` 拍平成 `evidence: string[]`，
  且**刻意不带行号**）——要可点击引文的清单**用不了这个面**，得走 7.1 那条 additive key。
- 另一个盲点顺手记下：`_conflicts_for` 只在 `subject_ref == project.ownerId` 时收人的冲突——
  **不带项目的人身上的 `team` 冲突，今天哪块屏都到不了**。
