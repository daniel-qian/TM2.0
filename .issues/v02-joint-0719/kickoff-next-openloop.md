### ① 「为什么要考虑韩文和日文？？？」

**他是对的，我上一棒把这条的分量夸大了。** 三个问号是准确的直觉。

我在验收单里用日韩名册论证 `6f838f3` 不能单独上。但**他的客户是中国公司**。
收工前我补跑了真实矩阵（直接 import `6f838f3` 的真 `parse.py` 调 `decode_text`）：

```
TW/Big5        declared=big5       correct=True     ← 繁体中文，对的
CN/GB18030     declared=gb18030    correct=True     ← 简体中文，对的
JP/ShiftJIS    declared=gb18030    correct=False    ← 编的
KR/EUC-KR      declared=gb18030    correct=False    ← 编的
```

原因：`gb18030` 和 `big5` **在同一级梯子里**，由 `_implausibility()` 打分裁决，所以中文两种都判对了。
日韩坏是因为 `shift_jis` / `euc_kr` **根本不在梯子上**，正确答案不可达。

**所以诚实的结论是：对他真实的客户群（中国公司、中文文件），`6f838f3` 单独上是净改善。**
我上一棒说「比不上还糟」，那句话对日韩文件成立，对他的实际用例不成立——**我把边缘情况说成了主线**。

⚠️ 但别把这条读成「那就上吧」。`a45bb4a` 仍然值得要，理由变了：
不是「防日韩伪造」，是**解码器从不说「我不确定」**——没有置信度字段，判错了也没有信号。
这个项目栽过的跟头全是这一类（编码没抽出人却回「已读入 ✓」、没读到状态却说 on-track）。
`a45bb4a` 补的是 `decode_confidence`。**用这个理由去跟他谈，不要再用日韩名册。**

### ② 「后端子集是啥」

大白话：**后端有一个正在线上跑的版本，和一个开发中的更新版本，中间差了 22 个改动。
「子集」= 从这 22 个里只挑 2 个上线，其余不动。**

为什么不整个上？因为里面夹着一条**建数据库表的改动**（`0008_account_contexts.sql`），

所以「挑着上」不是谨慎过头，是唯一安全的做法。

上一棒挑的那 2 条是：修中文编码读坏（就是 ① 那条）、修 `/advise` 出错时自己崩。
**结果一条都没上，后端至今原封不动。**

## 1. 这一棒的授权（比上一棒大得多）

> **边界只有两条：不许删数据库、不许删主工作树（`D:\avery`）。其余全自主。**

也就是说：push、改后端、重建镜像、换容器、填 Vercel 密钥、跑迁移、改 schema——**都不用问**。
Danny 睡了/不在线时照跑，不要停下来等批准。

但「授权」不等于「随便」。上一棒验证过的技术红线仍然成立，它们是**物理约束不是审批约束**：

* 🔴 **镜像里带 `0008_account_contexts.sql` = 生产库必然被建表，不可逆。**
  机制：`pg_registry.py:113` 的 `_ensure_schema()`（glob 在 :123）**无条件重放**所有
  `db/migrations/*.sql`，**没有迁移账本**，而且生产连的是 `postgres` **超级用户**，
  权限不足那条逃生分支永远不触发。build 前后各查一次。
  查表要用 **`avery.account_contexts`**，kickoff 里写的 `public.` 是**错 schema，假阴性发生器**。
* 🔴 **换容器必须带回滚**：时间戳命名 + 每条失败路径都调 `rollback()`，不许 `set -e` 直线脚本。
  地雷仍在：停着的容器 **`avery-prev` 还存在**，`docker rename` 撞名会中途 abort（上次挂了 1-2 分钟）。
* 🔴 **绝不 `npm install`**（所有 worktree 共用 `D:\avery\node_modules`）。
* 🔴 **不许跑全量 pytest**（`service/app.py` import 时加载真 key，≈11 分钟真实计费）。
* 🔴 **前端起在 5173**——后端 CORS 是精确匹配列表，换端口会被浏览器静默拦掉，
  症状是「团队/笔记/文件全空」，和真回归长得一模一样。
