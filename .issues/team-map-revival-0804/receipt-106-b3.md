板上就把对应的那一撮人和活拎出来——而且**镜头会跟过去**，不再出现「亮了，但那一簇在画面外，

## 票面四条逐条

### ① 搜索 + 部门 chips + 警报药丸 → 都是 focus 触发器；HUD 才许用视口单位

**做法：把三个触发器全部接到同一个真相源上。** B2 的 focus 真相源是 URL（`?focus=`），
B3 没有为 HUD 另立一套高亮状态，而是把 focus 的口从两种扩成四种：

| token | 谁点出来的 | 亮什么 |
|---|---|---|
| `person:<id>` | 板上的人 / 搜索结果 | 他 + 他 owned 的项目 |
| `project:<id>` | 板上的项目条 / 搜索结果 | 它 + owner |
| `zone:<部门>` | 部门 chip | 这一组人 + 他们背着的所有活 |
| `alert:needsYou` | 警报药丸 | blocked / at-risk 那几件 + 各自的 owner |

**副产品：三个触发器跟着一起可分享。** `?focus=zone:后厨` 发给合伙人，他打开看到的是同一屏。

单节点口与集合口只差一处：集合口**没有主角**，所以板上不会有任何节点长成 mini 卡——
一次组级提问要的是组级答案，不是随手挑一个人把他的卡打开。这一条落在 `MapNodeState` 上是
自然的（`subject` 态永远不出现），不需要额外分支。

**「缺了不编」只写了一遍**：四种口共用 `fromProjects()`——owner 缺席或指向一个不在花名册上的
id ⇒ 这根条自己亮、不画边、不点亮任何人。分四处各写一遍的话，将来只会有一处被改对。

**单一尺子（三处，一处都没有自己写 derive）：**
- 搜索走 `searchTeam`（顶栏搜索与引用菜单同一份）——同一个词在三处同一个结果。
- chips 直接吃 `layout.zones`（它本身就是 `deriveGroupFacets` 排出来的）。**不再调一次 derive**：
  再调一次就有了第二条链路，哪天两条不一致，chip 会指向一块板上不存在的分区。
- 药丸走新提出来的 `isNeedsYouStatus`（`projectView.ts`），与项目屏「需要你出手」那一栏
  **同一个函数**。药丸上的数与点开之后亮起来的条数由同一处决定——两处各写一遍的下场是
  药丸说 3 件、点开亮 2 根。

**🔴 人身零数字：chips 上没有人数。** `deriveGroupFacets` 现成就给了 `count`，这里刻意丢掉：
一排「后厨 4 · 前厅 2 · 客房 1」就是一张部门人数排行榜（ADR-0023 禁的形状）。
药丸上那个数是**项目**计数——项目可硬，人不可。

**HUD 落在画布外面（页头带里、进文档流），不是浮在板上的一块玻璃。**
第一版是浮的（画布左上角绝对定位），真机截图当场毙掉：初始镜头是 fit-width 顶锚，
板的左上角恰好在 HUD 底下——桌面上第一张部门卡的标签、手机上整个第一组，被搜索框和 chips
盖着。要保浮层就得让 `fitBoard` 知道 HUD 有多高（把镜头耦合到一个 DOM 尺寸），
而且 pan 之后照样会有东西钻到它底下。进流的代价是画布矮一截，买到的是**任何时候都没有东西
被自家工具条盖住**，桌面 1440 上 10 个部门 chip 还恰好一行铺得下。
它仍然是 HUD：不进 `TransformComponent`、不随镜头缩放，视口单位只有这一层能用。

**镜头跟随**（B2 收尾时点名留给 B3 的头号问题）三条口径：
① **已经全看得见就一个像素都不动**——demo-seed 那种板本来就装得下，B2 验过的手感一字不变；
② **只缩小、绝不放大**——放大读起来像「它替我决定了该看多近」；
③ 装不下才动，动就居中。
⚠ 有意识地允许缩到可读地板（`MIN_FIT_SCALE`）**以下**：手机竖屏上一个人与他的项目条相距
1100 board px，两头都进画面就只能缩到 0.30，那时字读不动。权衡是清醒做的——focus 只有一个
职责，就是把那条关系指出来，只框住一头等于没框；看不清可以捏合、可以「回到全景」原路退回，
看不见就是看不见。**初始帧仍守着地板**（那一帧回答的是「这家公司长什么样」，必须能读）。

**顺手修的三个真机问题（判据都看不见，靠人眼与像素）：**
- 搜索结果面板半透明 → 结果文字与底下的 chip 叠在一起两边都读不动。paper 皮的
  `--lite2-surface` 是 0.86，改成不透明。顶栏那个同款浮层没这个问题，只因为它浮在一片空白上。
- 部门 chips 恒**单行横滚**不换行：demo-seed 有 10 个部门，换行之后手机上 HUD 会长到半屏高。
- 地图的搜索框有**自己的提示语**（「在图上找人或项目…」）。匹配仍走顶栏那把 `searchTeam`，
  但桌面 /map 上两个框同时在画面里，照抄顶栏文案就是两个逐字相同的输入框干着两件事
  （那个开档案、这个点亮板上一撮）。「单一尺子」管的是一个词怎么算命中，不是这个框自称要干什么。

### ③ `assertRoomCanvas` 改判作用域

`.react-transform-wrapper` / `.lite-room-canvas` / `.lite-panzoom-wrapper` 三条从 `document`
全局查**收窄到 `.lite-room` 子树**。gate.md 那一行同批改。

**为什么必须改**：0729 那次翻转当时是对的——全站确实一块 pan/zoom 画布都不该有。
现在不是了：`/map` 是一整页 rzpp（PRD §0 的「pan/zoom 语法特区」，Danny 08-05 随方案 B 放行）。
全局写法今天**恰好**还绿，只因为本相位先点 Chat 标签、而 `/map` 在另一条路由上没挂载——
绿得靠巧合，不靠判据。任何一次把地图与对话屏放进同一棵树的改动都会让它红，而红的原因跟它
想守的那件事毫无关系，且长得像「对话屏又长出画布了」。

**死针探测**（`check-roomcanvas-b3.mjs`，**8 条全绿**）——收窄判据最常见的坏法是收到判不到
任何东西，所以这四个问题缺一不可：

| | 问什么 | 实测 |
|---|---|---|
| ① | 正常态它是绿的吗（对照基准） | `canvasGone = true` |
| ② | 往**对话屏里**塞一块画布，它红吗 | `false` —— 收窄之后仍有牙；撤掉回绿 |
| ③ | 往**对话屏外**塞一块画布，它还绿吗 | `true` —— 这正是收窄要买的 |
| ④ | 同一状态下**旧的全局写法**红吗 | `false` —— 所以这次改判真的有作用 |
| ⑤ | `/map` 上真有 `.react-transform-wrapper` 吗 | 有；且那一页没有对话屏——今天全局写法还绿靠的就是这个巧合 |

### ④ 像素基线

`eval-harness/visual/visual-map.spec.mjs` —— **3 态 × 2 皮 × 2 视口 = 12 张**，已冻并复跑零漂移。

另起一个文件而不是并进那两份，两个理由：`/map` 不在 `goScreen()` 的射程里（独立 path 常量，
刻意没进 `LiteScreen` 联合类型），硬塞进 `SCREENS` 数组会兜底回 home 把它又拍一遍还叫错名字
（#63 的 closerlook 白拍过两票）；而且一个 test 串多次 `toHaveScreenshot` **首处不匹配即中止**，
分文件 = 地图漂了不殃及九屏的漂移清单。

三态各自守的东西：
- `empty` —— 没有花名册时**不渲染空板**（PRD §3.6）。
- `calm` —— 骨架 + HUD-lite。自证要求 `.lite-map-chip` 在场：漏了它，B3 整层可以整个消失而
  基线全绿（那张图看着仍然「像地图」）。
- `focus` —— 票面写死的具名剧本 `person:u_小徐`，深链进。自证要求有连线且 mini 卡恰好一张：
  focus 没生效时拍到的是一张与 calm 几乎逐像素相同的图，冻进去等于凭空多一张永远不会红的基线。

`setFixedTime` 从第一天就钉上。地图自己的文案不读墙上时钟（到期日是文档原文），但基线拍的是
整个视口，壳（顶栏/铃铛/页脚）会读。新 spec 没有旧基线要作废，钉钟成本为零。

## 🔴 像素基线当场逮到一个判据全绿的真 bug

**`/map?focus=…` 直接打开时，镜头不跟随——亮着的那一簇整个在画面外。**

- 桌面 1440 上那一簇恰好装得下，所以**桌面那张基线、全部 62 条判据、人眼走查，一个都没发现**。
- 手机那张一眼就是坏的：小徐和草坪婚宴都不在画面里，板停在 fit 帧。
- 根因是**顺序**，不是别的：`onInit` 里框好镜头 → 紧随其后的被动 effect 又跑一次 `applyFit`，
  把它一把推回 fit 帧 → 最后只剩那条**动画版**的 `ensureVisible`。
- 而动画版在像素 spec 里永远走不完：`page.clock.setFixedTime` 冻住 `Date.now()`，
  rzpp 的动画进度正是拿它算的——**一冻，动画永远停在第 0 帧**。
- 修法是把首帧那次框选交给同一条 effect 并**不放动画**（`framedOnceRef`）：深链是「开门就该
  看见」，用户没点过任何东西，那段动画是在表演一个他没做过的操作。一件事只留一处。
- 补了判据 **H3**，而且**在手机视口上量**（桌面上它没有分辨力）。对照基准同时钉住：
  fit 帧下这一簇只有 1/3 在画面内，跟随之后 3/3。

一句话教训：**「桌面红≠手机红」不只是像素基线的规矩，也是行为判据的规矩**——
判据要落在分辨得出对错的那个视口上。

## 顺手发现，没顺手改（留给集成者）

**`eval-harness/visual/playwright.config.mjs` 的 `reducedMotion: 'reduce'` 实测没有生效。**
同一个 `use` 块里的 `locale` / `timezoneId` / `deviceScaleFactor` 都生效了，只有它没有：
页面里 `matchMedia('(prefers-reduced-motion: reduce)').matches === false`（playwright 1.61.1，
在 `page.clock` 之前就已经是 false）。而那份配置的头注释把它列为「确定性三板斧」之一。

**没在本票改**，理由：改了它等于给全部 54 张既有基线换一个渲染前提，那批基线是在
「动效**没**被关掉」的条件下冻的，一改就要整批重冻 + 人眼重审——那是另一票的活，
不该由一条顺手发现触发。B3 自己这 12 张不依赖它（首帧框选已改成**不放动画**，
本来就没有中间帧）。
