## 关键决策 / 结论

- **「DB 是最话痨的路径,库必须跟着服务器走」**(我提出,Danny 拍板执行)。演示机最终落在德国法兰克福后,实测 DB RTT:新加坡 **221ms** vs 法兰克福 **~15ms**,**15 倍**差距。一次 ingest 按 80 次数据库来回算 = 17.7 秒 → 1.2 秒。新加坡库当时只有 0 行、建了 2 小时,搬家几乎零成本 → 果断删库重建。
- **不用 client library 绕开直连串**(Danny 问的)。Avery 持久化层建在直连 Postgres + pgvector 上(`<=>` 余弦、HNSW 索引、召回全是 SQL),走 REST 拿不到原生向量查询,得把每个查询包成 PG 函数再 RPC——**等于把已验过的整层召回代码重写一遍**。结论:别为了省一个密码去重写好代码。
- **不在老 ECS 上抢跑部署**(我逆着 Danny 的授权劝住的)。那台只剩 ~150M free、无 swap、还扛着 ImaRead 全线,Avery ingest 峰值 300–600M → OOMKiller 很可能**误杀 ImaRead 的进程**,拿正在赚钱的产品赌几天早上线,不划算;且后端当时正在变(Ask 阶段 C 在施工),部了还得重部。等第二台机是对的。

## 踩坑 & 学到的

- **🔥 最该记住的教训:我自己的冒烟测试因为手动 `set search_path` 而「不忠实于 app 真实运行方式」,给了假信心。** 这是 vector schema 那个雷没能被早发现的直接原因——我的脚本加了拐杖,app 没有。此后所有验证都改为「**以 app 实际的连接方式复现**」(裸 `psycopg.connect`,不加任何参数拐杖)。这个教训在同一 session 里被引用了三次,每次都改变了我的做法。
- **SCRAM 通道绑定会被 libpq 误报成「password authentication failed」。** psycopg3/libpq 默认跟 Supabase pooler 协商 SCRAM-SHA-256-**PLUS**,而 Supavisor 协商不下来,libpq 报的却是密码错——**密码其实完全正确**。真解是连接串加 `channel_binding=disable`。这个误报让我一度断言「你手上那串密码 Supabase 不认,去重置吧」,差点让 Danny 白重置一次密码;是他坚持「密码应该就是这个没有错」,我才换了完全不同的排查方法把真因挖出来。**同一方法失败 2–3 次就该换方法,而不是加重结论。**
- **Supabase 直连域名 `db.<ref>.supabase.co` 是 IPv6-only**,IPv4 环境根本解析不出来 → 部署必须走 **session pooler** 端点。另:密码含 `/` 等特殊字符时,URI 里必须 percent-encode(`/` → `%2F`),否则会被当成路径分隔。建密码时直接设纯字母数字最省事。
- **`Path.glob()` 对不存在的目录返回 `[]` 且不抛异常** —— 这是 Dockerfile 漏 `COPY db/` 之所以**静默**的机理:`_ensure_schema()` 在容器里找不到 migrations 目录,却「成功地」什么都没做,迁移从不自动 apply。线上之所以还能跑,**纯粹因为 schema 是我带外手工建的**。凡是「遍历目录做事」的启动逻辑,目录缺失都应当是**响亮的失败**而不是空集合。
- **`CREATE EXTENSION vector` 不指定 schema 会跟着当时的 `search_path` 走。** 迁移里前面有 `SET search_path = avery, ...`,于是扩展装进了 `avery`;而 app 连接用的是**角色默认 search_path(不含 avery)**→ 每次 `/ingest` 报 `type "vector" does not exist` 500。修法是 `WITH SCHEMA public`——**public 是两种默认 search_path 都包含的唯一 schema**。
- **有些 bug 只在「全新库 / 全新部署」才炸。** 老库老容器一切正常,恰恰因为历史上的手工操作掩盖了自动化的缺失。所以**验证必须包含「从零自举」这一路**:重置库到 pristine → 让 app 自己建 schema → 打完整套件。这条现在是我的默认动作。
- **契约测试从没被跑过 ≈ 没有契约测试。** Ask 线在广播里自己写明「本机无凭据没实跑过」,我是第一个真跑他们 `@needs_db` 的人,一跑就塌一条。双实现契约测试的全部意义就是抓两个实现的行为分歧,而这条分歧真实存在:内存孪生 `if rec.answered_at: return "already"` 先短路、压根没碰时间戳参数;pg 孪生把它绑进 `answered_at = %s::timestamptz`(与 answer-once 原子锁同一条 UPDATE),**Postgres 先解析所有参数再过滤** → `InvalidDatetimeFormat` 当场炸。
- **对抗验证的 prompt 有偏置就会杀掉真发现。** 9 条发现全被反驳,我特意去看反驳者的**实际证据**而不是结论——他们真造了坏库跑全套(47 failed/5 passed,证明坏库是「最响亮」的状态而非静默)、真造了仿生产共享库跑新 0001(public 关系数 2→2、零字节写入、既有扩展未被搬动)、还做了反事实测试(去掉 break 后剩余迁移照样全失败 → break 不是因,权限才是)。理由够硬,这个 CLEAN 才值得认。
